# 需求发现指南

用于把粗略创意整理成项目规划输入。

## 创意简报

整理以下信息：

- 项目名称或暂定名
- 一句话概念
- 目标用户或玩家
- 核心问题、体验幻想或价值主张
- 平台：Web、移动端、桌面端、游戏引擎、CLI、API、嵌入式或混合形态
- 预期规模：原型、MVP、生产项目、内部工具或商业发布

## 澄清问题

只问会改变架构、范围或实现顺序的问题。可优先询问：

- 第一批真实用户是谁？他们一次使用中最需要完成什么？
- 这是验证想法的原型，还是需要长期维护的生产系统？
- 是否需要账号、支付、多人协作、实时同步、AI、离线能力或第三方集成？

如果用户不清楚如何回答，不要停住。给出 2 到 3 个可选方案，并说明每个方案对范围、技术架构、开发周期和后续扩展的影响。用户选择后继续规划。

如果用户没有回答，继续推进，并明确写出采用的假设。

## 方案建议格式

当用户无法确定方向时，使用这种格式：

| 选项 | 适合情况 | 优点 | 代价 | 对后续扩展的影响 |
| --- | --- | --- | --- | --- |
| 方案 A | ... | ... | ... | ... |
| 方案 B | ... | ... | ... | ... |
| 方案 C | ... | ... | ... | ... |

优先推荐一个方案，但保留其他可行选择。推荐理由要具体，不要只写“更好”。

## 范围拆分

将范围拆成：

- 第一期 MVP：能证明创意的最小完整体验，只包含核心闭环
- 后续短周期阶段：根据功能依赖、用户价值和技术风险继续规划，阶段数量不固定
- 暂缓功能：不阻塞 MVP 或当前阶段上线的高级能力

每个功能建议包含：

- 用户价值
- 需要的页面或系统
- 需要的数据
- 技术复杂度：低、中、高
- 依赖说明
- 对后续数据库和功能扩展的影响
