# 输出文档指南

用于在仓库中写入最终项目规划文档。完整项目规划默认必须创建或更新文档文件，不能只在对话中输出方案；只有当用户明确要求“只在聊天里回答”“不要写文件”时才跳过文件输出。

## 默认文件

除非用户指定其他名称，创建或更新以下文件：

- `docs/project-plan.md`
- `docs/technical-architecture.md`
- `docs/gameplay-design.md`

## `docs/project-plan.md`

包含：

- 项目概述
- 目标与非目标
- 目标用户
- 核心体验或玩法循环
- 功能范围：第一期 MVP、后续短周期阶段、暂缓功能
- 进度安排：根据项目复杂度规划 2 到 6 个或更多阶段，不固定三期
- 用户故事或玩家故事
- 实施里程碑
- 测试流程
- 后续维护清单
- 验收标准
- 风险
- 开放问题

## `docs/technical-architecture.md`

包含：

- 架构目标
- 技术栈推荐
- 必要时使用文本或 Mermaid 表示系统图
- 前端设计
- 后端设计
- 数据模型
- 数据库和功能可扩展设计原则
- API 草案
- 第三方集成
- 安全
- 测试
- 部署
- 可观测性
- 技术风险

## `docs/gameplay-design.md`

包含：

- 玩法概述
- 核心规则
- 单局流程
- 操作方式
- 胜利、失败和结算条件
- 计分规则
- 星级或评级规则
- 道具、奖励和广告关联
- 关卡模式和难度递进
- 游戏状态和边界情况
- 反馈表现：动画、音效、提示、震动
- 平衡性和可调参数

## 进度安排写作要求

进度安排不能机械固定三期。先判断项目复杂度、功能依赖和风险，再规划合适阶段数量。

- 简单项目可以 2 期。
- 中等项目通常 3 到 5 期。
- 复杂项目可以 6 期以上。
- 每一期尽量控制在 1 到 3 周。
- 第一期必须是 MVP，只验证核心闭环。
- 后续阶段逐步增加体验、效率、协作、运营、商业化、高级玩法或规模化能力。
- 每一期都要写清功能需求、数据库/架构变化、验收标准和扩展性说明。

## 写作规则

写成项目工作文档，不写营销文案。范围、进度安排和里程碑优先使用表格。只有确实未知的信息才保留 TODO。

## 文件输出要求

- 完整规划请求必须落地为文档文件。
- 如果 `docs/` 不存在，先创建 `docs/`。
- 如果默认文档已存在，更新对应内容，不要只追加重复段落。
- 默认不要创建 `docs/operations-workflow.md`。测试流程、发布流程、维护清单放入 `docs/project-plan.md`；只有用户明确要求操作流程文档时才单独创建。
- 最终回复必须列出已创建或更新的文档路径。
- 只有用户明确要求不写文件时，才只在对话中输出规划。
