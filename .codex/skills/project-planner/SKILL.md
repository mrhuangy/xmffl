# 项目规划助手

## 核心工作流

使用这个 skill 将模糊或早期的想法转化为可执行的项目方案。优先给出清晰假设、推荐路径和可落地任务，只有当缺失信息会明显影响方向时才追问。

1. 用一段话整理项目想法：目标用户、核心价值、平台类型和项目形态。
2. 识别关键未知项。最多只问三个会影响架构、范围或实现路线的问题；如果用户不清楚如何回答，给出 2 到 3 个方案建议供选择，并说明取舍。
3. 拆分项目范围：必须实现、应该实现、暂缓实现。
4. 设计体验流程：
   - App、网站、工具类项目：梳理主要用户旅程、页面、数据流、后台或运营需求。
   - 游戏类项目：梳理核心循环、单局流程、胜负条件、成长系统、操作方式、内容系统和反馈机制。
5. 设计技术架构：前端、后端、数据模型、存储、认证、第三方集成、部署、监控、测试和安全。
6. 制定进度安排：根据项目复杂度规划 2 到 6 个或更多短周期阶段，不固定三期；第一期必须是 MVP，后续阶段逐步增加体验、效率、协作、运营、商业化、高级玩法或规模化能力。
7. 规划数据库和功能边界时遵循“今日可实现、未来可扩展、后续可优化”，避免早期实体、字段、状态、模块职责设计过窄导致后期重构困难。
8. 拆分实施里程碑：具体任务、依赖关系、验收标准和风险点。
9. 完整项目规划必须输出文档文件。除非用户明确要求只在对话中回答，否则创建或更新：
   - `docs/project-plan.md`
   - `docs/technical-architecture.md`
   - `docs/gameplay-design.md`

## 规划风格

保持具体。能命名组件、页面、接口、数据表、状态机、模块和文件时就明确写出来。避免空泛的咨询式表达。

推荐技术栈时，优先遵循：

- 如果已有代码仓库，先贴合现有技术和目录习惯。
- 对个人或小团队项目，优先选择常见、稳定、维护成本低的方案。
- 基础设施保持朴素，除非创意本身确实需要特殊技术。
- 对成熟的游戏规则、物理、网络、解析、AI 或编辑器逻辑，优先使用可靠库或引擎。

当存在多个可行方案时，给出一个推荐路线，并补充一到两个替代方案及取舍。

## 参考文件

按需读取，不要一次性加载所有参考文件：

- 想法很粗略、需求不清时，读取 `references/discovery.md`。
- 输出最终项目文档前，读取 `references/output-docs.md`；完整规划默认必须创建文档文件。
- 规划开发进度、MVP、版本阶段或里程碑前，读取 `references/roadmap.md`。
- 编写技术架构文档前，读取 `references/architecture.md`。
- 项目包含游戏机制、可玩循环、关卡、成长或互动娱乐时，读取 `references/gameplay.md`。
- 编写测试流程、发布流程或维护清单前，读取 `references/operations.md`，并将内容合并进 `docs/project-plan.md`，不要单独创建操作流程文档，除非用户明确要求。

## 交付内容标准

完整规划请求通常需要包含：

- 项目概述
- 目标用户和问题定义
- 功能范围
- 按项目复杂度规划的多期进度安排
- 用户流程或玩法流程
- 技术架构
- 数据模型和 API 草案
- 数据库和功能可扩展性说明
- 实施里程碑
- 测试与验证计划
- 后续维护清单
- 风险和应对方案
- 创建或更新最终文档文件，除非用户明确要求只要对话回答

如果是在已有仓库中工作，先检查仓库结构，再让新文档与现有项目保持一致。
